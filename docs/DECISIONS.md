## 2026-09-21 — Заявки с сайта уходят в CRM через собственный бэкенд

**Решение:** формы сайта (`/anketa`, квиз на главной) шлют заявку на `POST /leads`
в `apps/api`, а тот передаёт её в публичную лид-форму CRM Tennet. Адрес формы —
переменная `CRM_LEAD_FORM_URL`, список разрешённых origin — `SITE_ORIGINS`.

**Причина:** раздел 4 ТЗ и требования S-04/S-10 — персональные данные и сведения
о здоровье уходят на собственный бэкенд в РК. Прокси даёт валидацию на границе,
ловушку для ботов и единственное место, где потом появится капча.

**Отвергнуто:** готовый `<script>` из конструктора Tennet — он рисует форму через
`innerHTML` с инлайновыми стилями и своим шрифтом, минуя токены `@amare/ui`, i18n
и `components/Links.tsx`, тянет на страницу с медданными скрипт Cloudflare Turnstile
и не переживает SSR. Прямой `POST` из браузера в `crm.tennet.kz` отвергнут по той же
причине, что и аналитика с ПД: данные ушли бы в чужой домен мимо нашего бэкенда.

**Известное ограничение:** публичная форма принимает только имя и телефон.
Давность события, подвижность, кто заполняет и UTM собираются анкетой, но в CRM
пока не доходят — `LeadsService` пишет об этом предупреждение один раз за запуск.
Снимается добавлением полей в конструкторе формы Tennet (поля лида `stroke_ago`,
`mobility`, `filled_by`, `utm` в CRM уже заведены).

## 2026-09-17 — Правила разработки: ECC + Impeccable + собственный документ

**Решение:** плагины ECC и Impeccable включены глобально. Правила ECC

**Причина:** плагин ECC не устанавливает правила сам, их нужно копировать вручную.
Копия в проекте фиксирует версию правил.

**Отвергнуто:** глобальные правила в `~/.claude/rules` — версия правил
менялась бы незаметно для проекта.

## 2026-09-17 — Стек и Docker

**Решение:** Node.js 24 + TypeScript, PostgreSQL 17, запуск через docker-compose.
Многоэтапный Dockerfile, приложение работает от пользователя `node`.
Порт БД наружу не публикуется.

**Причина:** одинаковое окружение на любой машине; в рабочем образе нет
dev-зависимостей и исходников TypeScript.

**Отвергнуто:** PostgreSQL 18 — в образе изменился путь хранения данных,
перейдём отдельной задачей при необходимости.

## 2026-09-17 — Монорепо Amare Care: pnpm + Turborepo, NestJS, Next.js

**Решение:** монорепо pnpm 12 + Turborepo. `apps/api` (NestJS, два процесса из
одного образа: `main.ts` — HTTP, `worker.ts` — без HTTP), `apps/site|care|staff`
(Next.js 16), `packages/ui|i18n|api-client`. Пакеты отдают TS-исходники
(«internal packages»), Next транспилирует их через `transpilePackages`.
Первый каркас (`src/index.ts`, корневой Dockerfile и compose) удалён.
Пункт «Порт БД наружу не публикуется» из записи выше остаётся в силе для prod.

**TypeScript 6.0, а не 7.0:** typescript-eslint 8.x поддерживает только TS < 6.1.
Переходим на TS 7, когда линтер его поддержит. api собирается SWC (`nest build`),
`tsc` — только проверка типов.

**Отвергнуто:** TS 7 с обходом peer-зависимости — риск неверной работы линтера;
Biome/oxlint — меньше правил для Next.

## 2026-09-17 — S3: Garage в однонодовом режиме

**Решение:** Garage v2.4 (`dxflrs/garage`), запуск `server --single-node --default-bucket`:
ключ и bucket создаются из `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_BUCKET`.
Admin API не включён. В плане был отдельный контейнер `s3-init` со скриптом
через Admin API — оказался не нужен.

**Причина:** MinIO community не публикует готовые образы; Garage лёгкий и активно развивается.

**Отвергнуто:** MinIO, SeaweedFS (тяжелее в настройке), init-скрипт через Admin API (лишний код).

## 2026-09-17 — Health: живость и готовность раздельно

**Решение:** `GET /health` — всегда 200, без зависимостей (для HEALTHCHECK Docker).
`GET /health/ready` — ping postgres, redis, s3; при сбое 503, причина только в логе сервера.

**Причина:** если liveness зависит от БД, Docker перезапускает здоровый API
при недоступной базе.

## 2026-09-17 — Три compose-файла

**Решение:** `compose.yaml` (база), `compose.override.yaml` (dev, подхватывается
`docker compose up` автоматически), `compose.prod.yaml` (явно через `-f`).
В dev порты postgres, redis и s3 публикуются **только на 127.0.0.1** — для локальных
инструментов. В prod наружу открыт только api. В контейнеры передаются только нужные
переменные, не весь `.env`.

**Причина:** `docker compose up` без флагов даёт dev; prod не запускается случайно.

## 2026-09-17 — Политики безопасности pnpm 12 не ослабляем

**Решение:** оставлены `minimumReleaseAge` (свежие релизы не ставятся) и блокировка
install-скриптов (разрешён только `@swc/core` в `allowBuilds`). Для слишком свежего
`@aws-sdk/client-s3` взята предыдущая версия вместо исключения из политики.

**Причина:** защита от подмены пакетов в цепочке поставок.

## 2026-09-17 — Дизайн-токены из набросков amare-site: Tailwind v4 в packages/ui

**Решение:** палитра (с контрастной темой), шрифты, радиусы, ширина контента, анимация,
базовые стили доступности и логотип перенесены из `amare-site` в `packages/ui`.
Tailwind v4, тема через `@theme inline` поверх RGB-переменных `--c-*` — имена классов
те же, что в набросках. Стандартная палитра Tailwind отключена. Палитра продублирована
в `palette.ts`; тест сверяет её с `tokens.css` и проверяет контраст (AA для обычной темы,
AAA для контрастной). Шрифты — `next/font/google`, раздаются с нашего домена.
Подробности — `docs/DESIGN_TOKENS.md`.

**Причина:** одна визуальная основа для site, care и staff; компоненты набросков переносятся
почти без правок классов; цвет вне бренда и регресс контраста ловятся автоматически.
В наброске шрифты грузились с fonts.googleapis.com — IP посетителя уходил в Google.

**Отвергнуто:** Tailwind 3 как в набросках (устаревшая ветка, миграция позже);
только CSS-переменные без Tailwind (компоненты пришлось бы переписывать);
генерация CSS из TS (лишний шаг сборки ради 13 значений — хватает теста сверки).

## 2026-09-17 — Публичный сайт из набросков amare-site в apps/site

**Решение:** публичная часть наброска (Vite + react-router) перенесена в Next App Router 1:1:
те же пути (`/napravleniya`, `/kurs-i-ceny`…), тексты и вёрстка. Совпадение проверено сравнением
текста и геометрии страниц с наброском на 1280 и 375 px. Общие компоненты без данных клиники
(Button, Reveal, ParallaxBand, SectionHeading, AccessibilityMenu, LanguageSwitch, cn) — в `packages/ui`;
всё, что знает о клинике (`lib/clinic.ts`, шапка, подвал, карта, секции), — в `apps/site`.

- **Сайт всегда в состоянии «гость».** Кабинеты уйдут в `care`; `/vhod` и `/kabinet/*` — редиректы
  на `NEXT_PUBLIC_CARE_URL`. Имя вошедшего в шапке вернётся с общей сессией site и care.
- **Библиотеки обновлены до поддерживающих React 19:** framer-motion 11 → `motion` 13,
  lucide-react 1.x, recharts 3, tailwind-merge 3. Правки кода — только тип `formatter` в графике.
- **Tailwind 3 → 4:** классы переведены официальной утилитой `@tailwindcss/upgrade` на копии наброска,
  разница межстрочных интервалов исправлена вручную (см. `docs/DESIGN_TOKENS.md`).
- **Запись:** заглушка API из `api/client.ts` — в `apps/site/lib/booking.ts`; неиспользуемая
  `fetchDoctorSlots` удалена (TODO про слоты остался у `getSlots`).
- **Фото — обычный `<img>`**, как в наброске (3.4 МБ). Переход на `next/image` — отдельная задача.

**Причина:** сайт на сервере отдаёт готовый HTML (поисковик видит контент — часть S-12 ТЗ);
перенос 1:1 позволяет сверять результат с наброском и не смешивать переезд с редизайном.

**Отвергнуто:** временно перенести вход и кабинеты в site (двойная работа);
ручная правка классов под Tailwind 4 (риск незаметных расхождений).

## 2026-09-17 — Кабинеты из набросков amare-site: apps/care (пациент, опекун) + apps/staff (специалист)

**Решение:** кабинеты наброска (`src/auth`, `src/pages/cabinet`, `src/components/cabinet`,
`src/api/client.ts`+`mockData.ts`) перенесены в два отдельных Next-приложения:
`apps/care` (`/vhod`, `/kabinet`, `/kabinet/pacient`, `/kabinet/opekun`) и `apps/staff`
(`/vhod`, `/` — рабочее место). В наброске все три роли жили в одном SPA; специалист
намеренно вынесен в отдельное приложение, не связанное с публичным сайтом.

- **Специалист не заходит через site.** `apps/site/lib/clinic.ts` больше не содержит
  `cabinetStaff` — на сайте нет ни одной ссылки на staff. `/vhod` и `/kabinet/*` на сайте
  по-прежнему редиректят в `care`, только для пациента и опекуна.
- **Мок-данные не синхронизируются между care и staff.** Это два разных процесса без общего
  бэкенда: назначение программы или сообщение специалиста в staff не появится в care без
  перезагрузки (и наоборот). В наброске это работало, потому что все роли делили один
  браузерный таб. Сознательное ограничение демо-режима, снимается вместе с реальным API.
- **Общие компоненты кабинета — в `packages/ui`:** `CabinetShell`, `DemoNotice`,
  `AttachmentChip`, `ChatPanel`, `BarthelChart` (переехал из `apps/site/components/home`).
  `ChatPanel` в отличие от наброска принимает `api: { getMessages, sendMessage }` пропом —
  у чата пациента с куратором (care) и чата специалиста с конкретным пациентом (staff)
  разная сигнатура доступа к данным.
- **Общие типы и демо-данные — в `packages/api-client`** (`src/cabinet.ts`): `Role`, `User`,
  `PatientCard`, `DayPlan`, `Message`, `Attachment` и т. д. Каждое приложение клонирует их
  в своё мутируемое состояние (`structuredClone`), как было в наброске.
- **Авторизация в каждом приложении своя** (`auth/AuthContext.tsx`, `auth/RequireAuth.tsx`):
  у care — выбор роли `patient`/`guardian`, у staff — единственная роль без выбора. Общий
  контекст в `packages/ui` не заведён: типы ролей у приложений разные, компонент вышел бы
  тоньше самого различия.

**Причина:** архитектура монорепо изначально разводит care и staff как отдельные приложения
(разные аудитории — пациенты/родственники и штатные специалисты, разный периметр доступа).

**Отвергнуто:** всё в apps/care по образцу наброска (проще, но специалист получил бы доступ
через тот же домен, что и пациенты); общий мок-бэкенд в apps/api для синхронизации care/staff
сейчас — раньше времени, это отдельная задача вместе с настоящим API.

## 2026-09-19 — Общий вход клиники: сотрудники входят вместе с пациентами

**Решение:** вход у клиники один — страница `/vhod` в `care`. На ней и демо-вход
пациента с опекуном, и блок «Сотрудникам клиники» со ссылками на роли куратора,
модератора и администратора. Рабочее место остаётся отдельным приложением `staff`
со своим периметром доступа: ссылка ведёт на `staff/vhod?role=<роль>`, и эта
страница сразу открывает рабочее место, не заставляя выбирать роль дважды.

- **Роль передаётся параметром, а не общей сессией.** Общей сессии между портами
  3002 и 3003 сейчас нет (у каждого приложения свой `localStorage`), и до бэкенда
  не будет. Значение приходит из адресной строки, поэтому проверяется по белому
  списку с обеих сторон: `staffLoginUrl()` в care и `isStaffRole()` в staff.
  Чужая строка в `?role=` просто показывает обычный экран входа.
- **Боевая авторизация у сотрудников — обычная: логин и пароль**, которые выдаёт
  администратор клиники. Заглушка будущего входа в `staff` переписана с «телефон +
  код» на «логин + пароль», и на обоих экранах написано, чего ждать: пациент и
  опекун входят по коду из SMS (аудитория 55+, пароль забудут или запишут на
  бумажке), сотрудник — логином и паролем. Роль и права придут с сервера вместе
  с учётной записью: выбор роли на клиенте, как сейчас в демо, — это повышение
  привилегий одной строкой в хранилище браузера.
- **`NEXT_PUBLIC_STAFF_URL` вшивается в care при сборке** (build-arg в
  `apps/web.Dockerfile`, по умолчанию `http://localhost:3003`), как это уже сделано
  с `NEXT_PUBLIC_CARE_URL` для сайта. Адрес публичный, не секрет.

**Причина:** отдельный вход для сотрудников приходилось знать наизусть — на сайте
он есть только ссылкой в подвале, а пациенты и персонал начинают с одной и той же
кнопки «Кабинет». Один вход — одна точка входа для всех ролей клиники.

**Что это меняет:** запись от 2026-09-17 «Специалист не заходит через site» —
в части входа. Разделение приложений и периметров доступа остаётся: сайт
по-прежнему не знает о внутренних маршрутах staff, care только открывает его вход.

**Отвергнуто:** слить `staff` в `care` одним приложением (у ролей разный периметр
доступа, это отменяло бы решение от 17.09 целиком); общий вход прямо на публичном
сайте (сайт остаётся гостевым, вход живёт в кабинете); передача роли через
`localStorage` общего домена (общего домена нет, появится вместе с бэкендом).

## 2026-09-19 — Мобильная вёрстка: правила вместо точечных заплат

**Решение:** поломки телефонной вёрстки в site, care и staff устранены общими
правилами, а не правками каждой страницы.

- **`viewport` с `viewportFit: 'cover'`** в `app/layout.tsx` всех трёх приложений.
  Без него `env(safe-area-inset-*)` на iOS всегда `0`, то есть липкие панели и
  кнопка SOS попадают под системную полосу жестов. `maximumScale`/`userScalable`
  намеренно не заданы: масштабирование пальцами нужно аудитории 55+ (S-13).
- **Безопасная зона — произвольными значениями Tailwind в местах использования**
  (`pb-[calc(0.75rem_+_env(safe-area-inset-bottom))]`), без токена в `packages/ui`:
  токен нельзя сложить внутри `calc`, а фиксированных панелей всего три.
- **Вкладки кабинета — горизонтальный скролл-трек до `sm`** вместо переноса.
  Перенос 7–8 вкладок съедал треть экрана до начала содержимого. Активная вкладка
  доскроллируется в видимую зону. Отвергнуто: `<select>` (ломает `role="tab"` и
  навигацию стрелками, сделанную намеренно) и drawer (лишний тап в ежедневном сценарии).
- **Календарь записи — резиновая сетка** (`flex-1` + `max-w-[22rem]`) вместо ячеек
  фиксированной ширины. Семь ячеек по 2.75rem требовали 346 px при 303 px доступных,
  и родитель обрезал их `overflow-hidden`: крайние дни месяца нельзя было нажать.
  Высота ячейки сохранена — крупные элементы управления это U-01 ТЗ.
  Отвергнуто: `clamp()` (магические числа) и `@container` (лишняя сущность ради одного компонента).
- **Кегль заголовков на телефоне снижен до `text-2xl`** (первый экран, `PageCover`,
  заголовки секций, квиз). Причина арифметическая: при базе 18 px слово
  «самостоятельность» занимает 479 px в `text-4xl` и 399 px в `text-3xl` при
  339 px доступных, а словарь переносов для русского есть не в каждом браузере.
  На `sm:` и выше кегли прежние.
- **Зона нажатия — утилита `tap-target`** (`packages/ui/src/styles/components.css`):
  псевдоэлемент растягивает область нажатия до 44 px, не меняя вид ссылки.
  Наращивать паддинги 17 ссылок подвала значило бы менять его ритм, то есть дизайн.
- **`overflow-x: clip` и перенос длинных слов в заголовках — только до 40rem.**
  `hidden` делает `html` прокручиваемым контейнером и ломает липкую шапку, поэтому `clip`.
  На десктопе ни то, ни другое не включается: обрезка спрятала бы уезжающие элементы
  вместо того, чтобы показать проблему, а `overflow-wrap: break-word` рвал слово
  в заголовке первого экрана, где оно и так помещается.
- **Высота ленты чата — `min(26rem, 60dvh)`**: `rem` растёт вместе с `--font-scale`
  до 1.3, и фиксированная лента становилась выше экрана.
- **График Бартел переведён на палитру и rem.** Цвета были литералами, не совпадали
  с палитрой и не реагировали на `data-contrast="high"`; кегли осей в px были
  единственным текстом проекта, который игнорировал `--font-scale`. Нижняя граница
  прозрачности поднята до 0.45 — иначе в контрастной теме столбики теряются.
- **Виджет доступности добавлен в кабинеты** (шапка `CabinetShell`). Ограничение:
  выбор не переносится между site, care и staff — это разные порты, у каждого свой
  `localStorage`. Снимется вместе с общим доменом.
- **Правила закреплены текстовыми тестами** над исходниками (образец — `palette.test.ts`):
  `packages/ui/src/styles/layout-rules.test.ts`, `apps/site/components/mobile-layout.test.ts`,
  `apps/care/components/mobile-layout.test.ts`, `apps/staff/app/viewport.test.ts`.
  Правило «сначала падающий тест» (раздел 4 правил) для геометрии CSS без DOM
  невыполнимо: тесты фиксируют не симптом, а правило, которым он лечится.
  Отвергнуто: jsdom/Playwright — новые зависимости и отдельное решение.

**Причина:** на 360–390 px ломались сценарии, а не только внешний вид: запись на
приём, навигация по кабинету, кнопка SOS, юрблок подвала под липкой панелью.

**Осталось за рамками:** `next/image` и вес фотографий (отдельная задача, см. запись
от 2026-09-17), планшетный диапазон 768–1023, поведение карусели врачей и логотипа,

## 2026-09-19 — Казахский язык: `/kk/` на сайте, хранилище в кабинетах

Сайт и кабинеты переведены на казахский. Словари — `@amare/i18n`, русский остаётся
эталоном ключей, казахский частичный с откатом на русский.

### Адреса сайта: две группы маршрутов вместо `app/[locale]`

Русская версия лежит в корне (`/kurs-i-ceny`), казахская под `/kk/`. Реализовано двумя
группами маршрутов с двумя корневыми макетами: `app/(ru)/` и `app/(kk)/`. У каждой свой
`<html lang>` — он честный уже в статическом HTML, а не проставляется скриптом.

- **Отвергнут `app/[locale]/…`:** он даёт `/ru/kurs-i-ceny`, а русский должен остаться в
  корне. Снять префикс можно только rewrite'ом (не работает при `output: export`) или
  перекладыванием папок в `scripts/build-static.sh` — а сайт собирается двумя способами
  (`apps/web.Dockerfile` и статика на FTP), пришлось бы поддерживать оба механизма.
- **Отвергнуто ручное дублирование 22 страниц:** расходится при первой же правке.
- Русские страницы остались файловыми, казахские собираются одним catch-all из реестра
  `apps/site/lib/pages.tsx`. Цена — казахские страницы тянут клиентские компоненты всех
  страниц сразу: +160 КБ JS против русской версии. Размер HTML при этом не вырос.
- `sitemap.ts` и `robots.ts` обязаны лежать в корне `app/`: из группы локали Next их
  не собирает (sitemap собирает, robots — нет; держим оба в одном месте).
- Полная перезагрузка при переключении языка — следствие двух корневых макетов,
  поэтому переключатель сделан ссылками `<a>`, а не `router.push`.

### Язык кабинетов — в localStorage, а не в адресе

`amare:lang`. Кабинеты за логином и закрыты от индексации: префикс `/kk/` не дал бы
ничего для поиска, а число экспортируемых страниц удвоил. На файловом хостинге сайт,
`/care/` и `/staff/` — один домен, поэтому хранилище общее и выбор с сайта доезжает до
кабинета. В разработке (порты 3001–3003) не доезжает — то же ограничение, что у виджета
доступности. **На сайте источник правды — только адрес:** сайт в хранилище пишет, но
никогда из него не читает, иначе казахский текст оказался бы на русском адресе и ушёл
в индекс.

### Что намеренно не переводится

- **`DEMO_*` в `@amare/api-client`** (~150 строк) — демо-данные, которые уйдут вместе с
  подключением бэкенда. Перевод в корзину, а расхождение ru/kk-демо пришлось бы
  поддерживать. В `DemoNotice` казахская версия объявляет это отдельной фразой.
- **Демонстрационные панели администратора и модератора в `apps/staff`** — русские
  строки в них служат значениями («Оплачено», «Не назначен») и участвуют в сравнениях;
  перевод сломал бы логику. Переведено то, с чем куратор работает каждый день.
- **Отзывы** остаются на языке автора: переводить чужую речь без его согласия нельзя.

### Локаль `en` убрана

Пакет объявлял `ru | kk | en`, но английской версии нет. Пустой словарь означал бы
«англичанин видит русский» — это хуже честного отсутствия. Вернуть — строка в `LOCALES`
и папка словарей.

### Требует вычитки носителем

Черновик казахского сделан ассистентом. Пометкой `[ВАЛИДАЦИЯ]` отмечены места, где
ошибка стоит дороже стиля: имена врачей (сверить с их документами), истории пациентов
(формулировка медицинского результата — утверждение от имени клиники), инструкции при
признаках инсульта и пояснения периодов восстановления в квизе, мнемоника УДАР
(в казахском она теряется — клиника решает, оставлять ли международный BE FAST).

`content.test.ts` (у каждой записи данных есть все ключи), `locale-routes.test.ts`
