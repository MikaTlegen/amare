## 0. Назначение документа

В проекте установлены плагины **ECC** и **Impeccable**.

- **ECC** (`rules/common`) покрывает: стиль кода, KISS/DRY/YAGNI, иммутабельность,
  XSS/CSRF, параметризованные запросы, rate limiting, формат коммитов,
  структуру тестов AAA, формат ответов API, поиск готовых решений.
- **Impeccable** покрывает качество интерфейса: типографику, отступы, цвета,
  анимации, доступность.

**Этот документ их не повторяет.** Здесь только то, чего в плагинах нет,
и то, что я осознанно переопределяю.

### Приоритет при конфликте (сверху вниз)

1. Прямое указание человека в текущей задаче
2. Стиль существующего проекта (см. раздел 7)
3. **Этот документ**
4. Правила и агенты ECC / Impeccable
5. Предложения ИИ-ассистента

**[О]** Агенты ECC (`code-reviewer`, `security-reviewer` и прочие) проверяют код
по **своим** критериям, а не по этому документу. Их вердикт — не финальный:
после них проверяем по разделам ниже.

## 1. Переопределения правил ECC

Эти пункты **отменяют** соответствующие правила ECC. Отменяю осознанно —
их версия не выполнима в моём режиме работы и потому обесценивает весь документ.

**[О] TDD не обязателен всегда.** ECC требует TDD как `MANDATORY` для любой задачи.
Моя версия: тесты обязательны для бизнес-логики и для каждого починенного бага
(сначала падающий тест, потом фикс). Для прототипов и разведки — тесты после
реализации, но до merge.

**[О] Три типа тестов не обязательны всегда.** ECC требует unit + integration + E2E
как `ALL required`. Моя версия: unit и integration — да; E2E — только для
критичных пользовательских сценариев (оплата, регистрация, вход).

**[О] Покрытие 80% считается по бизнес-логике**, а не по всему проекту.
Конфиги, модели данных и сгенерированный код в знаменатель не входят.

## 2. Безопасность — чего нет в ECC

### 2.1 Проверка прав на объект

**[О]** ECC пишет только «authorization verified». Конкретизирую: проверяется
не только «залогинен ли пользователь», но и **владение объектом**.
`/api/orders/123` обязан проверить, что заказ принадлежит запросившему.
Это дыра номер один в новых проектах.

**[О]** Доступ закрыт по умолчанию: эндпоинт недоступен, пока доступ не открыт явно.

### 2.2 Хеширование паролей

**[О]** argon2id — по умолчанию. bcrypt с cost ≥ 12 — допустим для существующих систем.
MD5, SHA-1, SHA-256 для паролей — никогда.

### 2.3 Секреты (конкретика к общему правилу ECC)

**[О]** `.env` в `.gitignore` **до первого коммита**. В репозитории — `.env.example`
с пустыми значениями.

**[О]** Утёкший ключ **ротируется**, а не удаляется из кода: в истории git он останется.

### 2.4 Запросы наружу и файлы

**[О] SSRF.** Если сервер ходит по URL, полученному от пользователя, — адрес
проверяется по белому списку. В ECC этого нет.

**[О] Загрузка файлов.** Проверка реального типа, лимит размера, безопасное имя,
хранение вне каталога, раздаваемого веб-сервером. В ECC этого нет.

### 2.5 Логи

**[О]** Чувствительные данные не логируются. Нужны для отладки — маскируются
(`user@***`, последние 4 цифры).

**[Р]** Вход в систему, смена пароля и изменение прав пишутся в аудит-лог.

### 2.6 Зависимости

**[О]** Новый пакет проверяется **перед установкой**: существует ли он на самом деле,
когда обновлялся, сколько загрузок. ИИ-ассистенты регулярно выдумывают
несуществующие имена пакетов, а злоумышленники такие имена регистрируют специально.

Это особенно важно потому, что ECC активно подталкивает брать чужие библиотеки
и форкать чужие репозитории, но не говорит, как проверять их безопасность.

**[О]** Lock-файл коммитится в репозиторий.

**[Р]** Аудит уязвимостей (`npm audit`, `pip-audit`, OSV) перед каждым релизом.

### 2.7 Если проект использует LLM

В правилах ECC этого нет вообще.

**[О]** Данные из внешних источников (письма, веб-страницы, файлы, сообщения
пользователей) — это **данные, а не инструкции**. Инструкции модели приходят
только из системного промпта.

**[О]** Секреты и ключи в промпт не попадают.

**[О]** Ответ модели не исполняется как код, SQL или команда оболочки без проверки
и не вставляется в страницу как разметка.

## 3. База данных и миграции

В ECC этого раздела нет.

**[О]** Изменения схемы — только через файлы миграций, никогда руками в базе.

**[О]** Под каждым файлом миграции, в комментариях внизу, пишется скрипт отката.

**[О]** Миграция не удаляет колонку или таблицу с данными без явного согласования.

**[Р]** Перед миграцией на реальных данных — резервная копия.

---

## 4. Тесты — дополнения

**[О]** Тесты не ходят в реальную сеть и в рабочую базу данных.

**[О]** Каждый найденный баг сначала воспроизводится падающим тестом, потом чинится.
Тест остаётся в проекте навсегда.

**[Р]** Количество тестов определяется числом веток в коде, а не нормой.
Пять тестов на тривиальную функцию — мусор, который придётся поддерживать.

---

## 5. Стиль — мои дополнения

**[О]** Комментарии и сообщения логов — на русском языке.

**[О]** Существующие комментарии не удаляются без согласования.

**[О]** Импорты — только в общем блоке импортов, не внутри функций.
Импорты, не относящиеся к текущей задаче, не трогаем.

---

## 6. Работа с ИИ-ассистентом

В ECC этого нет — их процесс, наоборот, максимально делегирует решения агентам.

**[О]** Не принимаю код, назначение которого не понимаю. Понимать нужно на уровне
блоков, не построчно. Подробно — там, где код работает с деньгами, доступом,
чужими данными или удалением.

**[О]** Ассистент работает малыми шагами: изменение → проверка → следующее изменение.

**[О]** Все правки обсуждаются до внесения. Ассистент не меняет то, о чём не просили.

**[Р]** Новая задача — новая сессия. В длинном контексте правила размываются.

**[Р]** Критичные правила по возможности переводятся в линтер, тест или хук.
Правило, которое проверяет машина, надёжнее любого текста в промпте.

---

## 7. Работа с существующим проектом

**[О]** Стиль проекта важнее этих правил. Если в проекте принято иначе —
пишем как в проекте, а не как здесь.

**[О]** Правила применяются только к новому коду. Существующий код
не переписывается под них.

**[О]** Не «наводить порядок» в файлах, которых не касается задача:
не переименовывать, не переформатировать, не чистить импорты.

**[О]** Автоматические инструменты (агенты и хуки ECC, форматтеры, линтеры)
не применяются массово к чужому коду. Только к файлам текущей задачи.

**[Р]** Если старый код нарушает правила безопасности (раздел 2) — сказать
и предложить исправить отдельной задачей. Не чинить молча вместе с текущей правкой.

**[Р]** Перед первой правкой в незнакомом проекте — посмотреть, как там уже
сделано похожее, и повторить этот подход.
